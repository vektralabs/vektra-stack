## Overview

This plan replaces the Phase 1 minimal HTML dashboard (inline HTML string in `api.py`) with a proper HTMX + Jinja2 admin UI. Five pages are delivered: health dashboard, API key management, namespace management, audit log viewer, and system config viewer. All pages follow the same pattern: authenticate, call the existing REST API, render the response as HTML. No business logic lives in templates or in the admin page routes, preserving a clean migration path to a separate SPA in Phase 3 (ADR-0024).

The UI uses HTMX for partial page updates (table pagination, form submissions, status polling) without full page reloads. CSS is provided by a classless stylesheet (Pico CSS or similar, served as a static file) so no build pipeline is required. The HTMX library (~14KB) is also served as a static asset, avoiding CDN dependencies for on-premises deployments.

The existing Phase 1 `GET /admin` endpoint is replaced by a multi-page layout. The health dashboard remains the landing page at `/admin/`, with navigation links to `/admin/keys`, `/admin/namespaces`, `/admin/audit`, and `/admin/config`. Each page route is a thin presentation handler that calls the corresponding REST API endpoint using httpx (internal HTTP call) or by directly invoking the service layer, then passes the data to a Jinja2 template.

## Design Notes

**Template structure**:
```
vektra-admin/src/vektra_admin/
  templates/
    base.html          - base layout: HTML head, nav bar, content block, footer
    health.html        - health dashboard (component table, memory stats)
    keys.html          - API key list + create form + revoke buttons
    namespaces.html    - namespace list + create form + delete buttons
    audit.html         - audit log table with filter form and pagination
    config.html        - read-only config display (env vars, versions)
    partials/
      health_table.html    - component health table (HTMX partial for polling)
      keys_table.html      - API key table (HTMX partial for after create/revoke)
      namespaces_table.html - namespace table (HTMX partial for after create/delete)
      audit_rows.html      - audit log rows (HTMX partial for pagination)
  static/
    htmx.min.js        - HTMX library (~14KB, vendored)
    pico.min.css        - Pico CSS (~10KB, vendored) or similar classless CSS
    admin.css           - minimal custom styles (status colors, layout tweaks)
```

**No business logic in templates (ADR-0024 constraint)**:
- Template variables are plain dicts/lists prepared by the route handler
- No database queries in route handlers - call REST API endpoints instead
- No conditional logic beyond simple display (show/hide based on data presence)
- Jinja2 filters limited to formatting (date formatting, truncation)

**Internal API calls**:
- Route handlers call the REST API endpoints using the same FastAPI app's TestClient pattern, or more practically, by importing and calling the underlying service functions directly (avoiding HTTP overhead for same-process calls)
- Preferred approach: route handlers call the same underlying functions that the REST API routes call (e.g., `_health.check_all()` for health, direct SQLAlchemy queries for keys/namespaces/audit)
- This keeps the "no business logic in templates" constraint while avoiding unnecessary HTTP round-trips
- When Phase 3 migrates to a separate SPA, these internal calls are replaced by external REST API calls from the SPA's frontend

**Authentication for admin pages**:
- All `/admin/*` routes require admin scope via Bearer token
- Token passed as query parameter (`?token=...`) or stored in a browser cookie after first auth
- Cookie name: `vektra_admin_token`, HttpOnly, SameSite=Strict, Secure (when behind TLS)
- Cookie set by a login handler: `POST /admin/login` accepts token in form body, sets cookie, redirects to `/admin/`
- HTMX requests include the token via `hx-headers` attribute on the body element

**Health dashboard (`/admin/`)**:
- Calls `_health.check_all(registry, version)` for deep health response
- Displays component table with status, latency, message columns
- Status badges with color coding (green/yellow/red)
- Memory stats section from `_health.check_memory()`
- Auto-refresh via HTMX polling: `hx-get="/admin/partials/health" hx-trigger="every 30s"`

**API keys page (`/admin/keys`)**:
- Lists all keys via SQLAlchemy query (same as `list_api_keys` handler)
- Create form: label (text), scopes (checkboxes: admin, ingest, query)
- Create action: `hx-post="/admin/keys/create"` -> calls `generate_key()` and persists -> returns updated table partial + flash message with the plaintext key (shown once)
- Revoke action: `hx-delete="/admin/keys/{id}"` -> soft-deletes -> returns updated table partial
- Key display: preview only (first 8 chars), created date, scopes, status (active/revoked), last used

**Namespace page (`/admin/namespaces`)**:
- Lists namespaces via SQLAlchemy query on namespace table
- Create form: name (text), owner (text, optional)
- Delete action: `hx-delete="/admin/namespaces/{id}"` -> soft-delete -> returns updated table partial
- Shows document count per namespace (joined from source_documents)

**Audit log page (`/admin/audit`)**:
- Displays audit entries with: timestamp, key_preview, endpoint, method, status_code, action
- Filter form: date range (start/end), endpoint filter (dropdown), status code filter
- Server-side pagination: cursor-based using audit log ID (descending order)
- Page size: 50 entries per page
- Navigation: "Older" / "Newer" buttons using HTMX with `hx-get` and cursor parameter
- Partial: `hx-get="/admin/partials/audit?cursor={id}&direction=older"` returns rows only

**Config page (`/admin/config`)**:
- Read-only display of system configuration
- Shows: version, VEKTRA_* env var values (with secrets masked), active providers, database status
- No mutations, no HTMX interactivity needed
- Env var masking: values containing "KEY", "SECRET", "PASSWORD", "TOKEN" are displayed as "****"

**Dependencies to add to vektra-admin/pyproject.toml**:
- `jinja2>=3.1` (for template rendering)
- `python-multipart>=0.0.9` (for form data parsing in HTMX POST requests)

## Testing Approach

Unit tests verify the auth dependency (cookie extraction, token validation, rejection), secret masking function, and template rendering with known input data. Integration tests use httpx with the full FastAPI app (TestClient), exercising each page route and HTMX partial endpoint. The CRUD flows for keys and namespaces are tested end-to-end: create, verify in list, delete/revoke, verify state change. Audit log pagination is tested by inserting known entries and navigating with cursor parameters. Template rendering correctness is verified by checking for expected HTML elements in the response body (status badges, table rows, form inputs).

## Integration Notes

The UI router is mounted on the main FastAPI app alongside the existing API router. Static files are served via FastAPI's StaticFiles mount at `/admin/static`. The Jinja2Templates instance is configured in `ui.py` and points to the templates directory within the vektra_admin package.

Authentication reuses the existing KeyStoreProvider from the ProviderRegistry. The cookie-based auth is a convenience layer for browser sessions - the underlying token validation is identical to the Bearer token validation used by API endpoints.

The admin-enforcement plan (Wave 1) must be completed first because the UI depends on namespace CRUD endpoints and audit log query endpoints existing. If those endpoints are not yet available, the corresponding pages cannot be implemented. The health dashboard and API keys page could technically be built with Phase 1 endpoints alone, but the plan is designed to be executed as a single unit after admin-enforcement.

infra-phase2 (Wave 5) registers the UI router in the app lifespan and ensures static files are included in the Docker image.
