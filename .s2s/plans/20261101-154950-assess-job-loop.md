## Overview

This plan builds the runtime of `vektra-assess-worker` (COMP-003): a single asyncio process that claims
leased jobs from `assess_jobs`, runs them under per-kind concurrency pools with hard timeouts, runs
periodic ticks under advisory locks, writes a heartbeat, and shuts down cleanly. It also provides the
API-side outbox helper (insert job + empty NOTIFY in the caller's transaction) and the chaos harness
that later plans reuse to prove their handlers survive `kill -9` and Postgres restarts.

It is deliberately the **framework only**. Every domain handler body (pre-flight, sweeper, reaper,
outage probe, enrolment re-check, transcript generation, delivery, gate-input refresh, purge, setup
check) belongs to a later plan; here each is registered as a named slot with its schedule, budget and
lease, and the slot fails closed if no body has been bound (see the ownership table in Design Notes).

There is no precedent to build on: `docker/entrypoint.sh` knows only `server` and `migrate`, arq has
never run (`registry["arq_pool"]` is never registered, `vektra_ingest/api.py _enqueue_ingest_job`
always falls back to FastAPI `BackgroundTasks`), no stale-job reaper exists, and the documented
ADR-0006 5-minute recovery rule does not exist in code. The loop is greenfield and must be proven
empirically, by row counts, not by status fields.

## Design Notes

**Module layout** (inside `vektra-assess/src/vektra_assess/`):
- `jobs.py` — API-safe outbox helper `enqueue_job(conn_or_session, kind, ref_id, not_before=None)` and
  the `JobKind` enum. Importable by the API. Contains no worker code.
- `worker/runtime.py` — `WorkerRuntime` (claim loop, pools, ticks, heartbeat, shutdown).
- `worker/runner.py` — the `JobRunner` Protocol and `HandlerSpec` / `TickSpec` dataclasses.
- `worker/listener.py` — dedicated persistent asyncpg control connection (LISTEN + advisory locks).
- `worker/sql.py` — claim / complete / fail / release / reclaim statements (raw SQL, asyncpg).
- `worker/reconcile.py` — startup reconciliation pass.
- `vektra-app/src/vektra_app/assess_worker.py` — composition root: settings, DB pool, KEK and
  injected providers (from later plans), handler binding, sys.modules assertion, `main()`.

**JobRunner interface** (the Phase-2 arq seam, ARCH-068): `register_handler(HandlerSpec)`,
`register_tick(TickSpec)`, `run()`, `stop()`. A handler is `async def handle(ctx: JobContext) -> None`
where `JobContext` carries only `job_id`, `kind`, `ref_id`, `attempt`, a DB acquire function and a
logger. Handlers receive **no job args beyond the reference id** and MUST re-read and re-validate the
authoritative rows (session state, epoch, transcript/recipient state) inside their own transaction
before acting; acting on a stale job is a no-op that completes the job.

**Claim** (fenced): `UPDATE assess_jobs SET state='running', lease_until=now()+$lease, attempts=attempts+1,
claimed_by=$worker_id WHERE id IN (SELECT id FROM assess_jobs WHERE kind = ANY($kinds) AND (state='ready'
OR (state='running' AND lease_until < now())) AND not_before <= now() ORDER BY not_before, id LIMIT $free
FOR UPDATE SKIP LOCKED) RETURNING id, kind, ref_id, attempts`. `$free` is the number of free slots in
that kind's pool, so a pool is never over-claimed. Completion, failure and release all carry
`WHERE id=$id AND claimed_by=$worker_id AND attempts=$attempt` (fencing token): a worker whose lease was
reclaimed cannot overwrite the newer claim. A rowcount of 0 is logged as `assess_job_fence_lost`.

**Leases and budgets**: lease ≈ 2 × budget; no lease renewal (a handler that needs longer than its
budget is a bug, not a renewal case). Defaults (settings `VEKTRA_ASSESS_JOB_<KIND>_{CONCURRENCY,BUDGET_S,LEASE_S,MAX_ATTEMPTS}`):

| Pool | Kinds | Concurrency | Budget / lease |
|------|-------|-------------|----------------|
| preflight | `preflight` | K (`VEKTRA_ASSESS_PREFLIGHT_CONCURRENCY`, placeholder 10 per NFR-020) | 45 s / 90 s |
| ws | `enrolment_check`, `gate_refresh`, `render_check` | 2 | 20 s / 40 s |
| transcript | `transcript_generate` | 2 | 30 s / 60 s |
| delivery | `transcript_deliver` | 2 | 30 s / 60 s |
| maintenance | `reconcile_reply`, `purge`, `setup_check` | 1 | 60 s / 120 s |

Pools are separate `asyncio.Semaphore`s, so a WS or SMTP stall never starves pre-flight, and ticks run
on their own tasks outside every pool (COMP-003). Hard timeout = `asyncio.timeout(budget)`; on timeout
or exception the job is released with `not_before = now() + backoff(attempt)` (exponential, jittered,
capped); after `max_attempts` it becomes `state='dead'`, emits a content-free audit event and increments
`assess_jobs_dead_total`. Exact pre-flight budget vs the REQ-071 commit window T is confirmed by plan
20261101-154950-assess-session-lifecycle.

**Wake-up**: `enqueue_job` runs `INSERT ... ; NOTIFY assess_jobs` in the caller's transaction, so the
notification is delivered only at commit (outbox). Payload is always empty (INT-002). The worker's
control connection LISTENs and sets an `asyncio.Event`; the claim loop waits on that event with a 1 s
timeout, so the 1 s poll is the correctness backstop and NOTIFY is only a latency hint.

**Control connection**: one persistent asyncpg connection outside the pool
(`application_name=vektra-assess-worker-control`). It LISTENs and also holds the session-level
`pg_try_advisory_lock(key)` for ticks (calls serialized by an `asyncio.Lock`). This keeps the connection
budget at pool 5 + 1 (INT-002). If the control connection drops, the server releases all locks: every
running tick is cancelled (it is no longer fenced), the listener reconnects with backoff, and ticks
resume on the next schedule. A startup self-test LISTENs, NOTIFYs and requires delivery within 2 s;
failure is a `StartupValidationError` naming transaction-mode poolers (ARCH-068 consequence).

**Tick framework**: `TickSpec(name, interval_s, jitter_s, timeout_s, lock_key, run_on_startup)`. A tick
is skipped (not queued) if its previous run is still in flight or the lock is held elsewhere. Lock keys
are stable constants in one module (`vektra_assess.worker.locks`), collision-tested. Ticks enqueue jobs
or do bounded DB work; external I/O happens outside DB transactions (existing short-lived-session pattern).

**Handler/tick ownership** (bodies bound later; until bound, a registered slot raises
`HandlerNotBound` and the worker refuses to start if `VEKTRA_ASSESS_ENABLED=true` — fail closed, no
silent no-op):

| Slot | Schedule | Body owned by |
|------|----------|---------------|
| `preflight` job | on Start (outbox) | 20261101-154950-assess-session-lifecycle |
| sweeper tick (deadline, C cap, grace) | 10-15 s | 20261101-154950-assess-session-lifecycle |
| STARTING reaper tick | 15 s, lease ≈ 90 s | 20261101-154950-assess-session-lifecycle |
| outage probe tick | 5-10 s per provider | 20261101-154950-assess-session-lifecycle |
| `reconcile_reply` job ("risposta interrotta") | from sweeper/reconcile | 20261101-154950-assess-session-lifecycle |
| enrolment re-check tick | 60 s | 20261101-154950-assess-session-lifecycle (over plan 4 WS readers) |
| gate-input refresh tick, `render_check` job | per design default | 20261101-154950-assess-session-lifecycle (over plan 4 WS readers) |
| `transcript_generate` job | on CLOSED (outbox) | 20261101-154950-assess-transcript-delivery |
| delivery retry tick, `transcript_deliver` job | by `not_before` | 20261101-154950-assess-transcript-delivery |
| daily purge tick | daily | 20261101-154950-assess-privacy-retention |
| daily setup-check tick | daily + on startup | 20261101-154950-assess-moodle-ws (contributors: parser ping from plan 5, SMTP probe from plan 10) |
| heartbeat tick | 5 s | **this plan** |
| done-job cleanup tick | hourly | **this plan** |

**Startup order**: config → DB pool → control connection + NOTIFY self-test → sys.modules assertion →
bind handlers (all slots bound or refuse) → reconciliation pass (under the `reconcile` lock: release
expired `running` leases to `ready`, run every tick with `run_on_startup=True` once, in a fixed order) →
heartbeat state `ready` → start claiming. No claim happens before reconciliation completes.

**Shutdown** (SIGTERM, PID 1 via `exec` in entrypoint): stop claiming → wait up to
`VEKTRA_ASSESS_WORKER_DRAIN_S` (default 20 s, < `stop_grace_period` 30 s) for in-flight handlers →
cancel the rest and release their leases (`state='ready', lease_until=NULL`, fenced) → heartbeat state
`stopped` → close pool and control connection → exit 0. A released job is picked up by the next
worker immediately rather than after lease expiry.

**Heartbeat**: the heartbeat tick upserts `assess_heartbeat` (worker_id, started_at, beat_at, state,
version, per-pool in-use counts, oldest ready job age) and touches `/run/assess-worker/heartbeat` on
tmpfs. The file is touched from the scheduler loop only (proves the event loop is not wedged); the row
proves DB-reachable progress. `/health/assess` (registered by plan 1, readiness only, not feeding shallow
`/health`) reads the row: heartbeat age > 60 s or oldest ready job age > 30 s ⇒ not ready.

**Connection budget** (INT-002, `max_connections` 100): worker pool `pool_size=5, max_overflow=0,
pool_timeout=5` + 1 control = 6. Today the API's `vektra_shared/db.py init_db` defaults are 10 + 20
(max 30), above the ~15 INT-002 assumes; this plan documents the budget and adds a test, it does not
silently change the main API pool (that would alter non-assess behaviour; see Notes).

## Acceptance Criteria

- [ ] Under concurrent runtimes and 500 jobs, every job is executed to `done` and the side-effect table
      has exactly 500 rows: 0 double executions, 0 lost jobs (REQ-067, REQ-075 durability base)
- [ ] `kill -9` of the worker mid-handler, then restart: after lease expiry the job completes; row counts
      show effects = jobs, 0 `running` with expired lease, 0 `dead` (ARCH-068 chaos; REQ-070/REQ-071 base)
- [ ] Postgres restart (container restart and backend termination) during load: the worker reconnects
      without manual action, LISTEN is re-established, and all jobs reach `done` (row counts)
- [ ] With NOTIFY suppressed, a committed job is claimed within 1.5 s by the poll fallback; a job from a
      rolled-back transaction is never claimed (0 rows ever `running`)
- [ ] With the WS pool saturated by stalled handlers, pre-flight jobs are still claimed up to K in
      parallel and ticks keep firing (heartbeat age < 10 s measured from the row) (COMP-003, NFR-020)
- [ ] No claim is issued before the reconciliation pass completes (statement log ordering in test)
- [ ] SIGTERM drains and releases: exit 0 within 30 s; released rows `ready`, `lease_until IS NULL`
- [ ] Worker refuses to start (non-zero exit, structured `[STARTUP ERROR]`) when: a production slot is
      unbound; a forbidden module is in `sys.modules`; NOTIFY self-test fails; lease < 2 × budget
- [ ] Idle RSS of the worker entry ≤ 300 MB measured from `/proc` in CI (ARCH-073)
- [ ] `pg_stat_activity` count for `application_name LIKE 'vektra-assess-worker%'` never exceeds 6
      during the 500-job load test (INT-002)
- [ ] `pg_class.reloptions` for `assess_jobs` contains the autovacuum and fillfactor settings; after
      cleanup, `done` rows older than retention = 0
- [ ] `/health/assess` reports not-ready within 65 s of `docker stop` of the worker while shallow
      `/health` stays 200 (ARCH-068 liveness; plan 1 endpoint, this plan's row)

## Testing Approach

Three layers. Unit tests (no DB) cover SQL text, backoff maths, tick scheduling with a fake clock, and
slot registration. Integration tests (`@pytest.mark.integration`, testcontainers
`PostgresContainer("pgvector/pgvector:pg16")`) run real runtimes against real Postgres for claim
exclusivity, fencing, timeouts, LISTEN/NOTIFY, advisory locks and shutdown. The chaos harness runs the
worker as a subprocess and injects `kill -9` and Postgres restarts; every assertion is a row count over
`assess_jobs` and the harness's effect table, never a status field reported by the worker itself.

### Test Infrastructure

- **Required**: Docker (testcontainers pg16 with a fixed host-port binding for restart tests); Linux
  `/proc` for the RSS test; the chaos harness subprocess composition
- **Provided by**: tasks in section D of this plan; testcontainers already used by the repo; assess CI
  job from 20261101-154950-assess-foundations
- **False-pass guard**: integration and chaos tests are collected under `-m integration` and are listed
  in `tests/test_suite_execution_coverage.py`, so a suite not run by both `make test` and CI fails the
  structural guard; the RSS test calls `pytest.skip` only off Linux and the CI job asserts
  `skipped == 0` for the `assess-chaos` job via the junit report

  forever; the compose service must override it (task C). Forgetting this is silent in `docker compose up`.
- **Connection budget risk**: the main API pool (10 + 20) plus an assess API pool plus worker 6 must
  stay under 100; INT-002 assumed ~15 for the API. Shrinking the main pool changes non-assess
  behaviour and is left to an explicit decision in 20261101-154950-assess-hardening-release.
- **pgbouncer**: transaction-mode poolers break LISTEN and session advisory locks; the NOTIFY self-test
  turns this into a startup refusal rather than a silent 1 s-poll-only degradation.
- **OQ-026 / OQ-032**: K and the 512M limit depend on hardware; the idle-RSS figure with `litellm`
  imported is an input to that decision. A pre-flight budget vs T mismatch is resolved in plan 8.
- **Schema drift found by task A1 (2026-11-03), decision: the runtime adapts to the schema, not the other
  way round.** Plan 2 delivered `assess_jobs` and `assess_heartbeat` in revisions 0013-0017, which are
  applied and already used by the API (setup-check, lifecycle definer functions). They differ from the
  contract this plan was written against, and renaming them would break those callers:
  | Plan text | Schema in 0013 | Runtime uses |
  |---|---|---|
  | state `running` | `leased` (also `failed`, unused) | `leased`; a failed attempt goes back to `ready` with a `not_before` backoff, an exhausted job to `dead`; the table's `failed` state is not used |
  | `ref_id` | `args` JSONB (ids only, < 1 KiB) + `dedupe_key` | `args`; handlers read ids from `args` |
  | `claimed_by` | `leased_by` | `leased_by` |

- **Outbox helper vs the API role (task A3, 2026-11-03)**: the API role has INSERT on `assess_jobs` and
  nothing else, and both `RETURNING` and `ON CONFLICT` need SELECT, so a first version of
  `enqueue_job` failed with `permission denied` on a real Postgres. The helper does a plain INSERT
  inside a SAVEPOINT and reads a unique violation on `uq_assess_jobs_dedupe` as "already queued". It
  returns a bool (inserted or not), not the id. The grant matrix is unchanged on purpose: widening the
  API role's read access to the job table is a DB-boundary decision, not a convenience. The helper is
  listed in import-linter contract (c) and in the parser sidecar's forbidden list.
- **Claim and release semantics (task B2)**: the claim also requires `attempts < max_attempts`, so an expired
  lease on an exhausted job is never re-run; startup reconciliation and a periodic pass move it to `dead`
  (`lease_expired_exhausted`). A shutdown release does not count as an attempt (`attempts` is decremented),
  otherwise a deploy would burn the retry budget of every in-flight job. Both are proven on a real
  Postgres as the worker role (two concurrent claimers never return the same row; a stale worker's late
  `complete` matches zero rows and leaves the newer claim untouched).
- **Settings shape (task B4)**: the plan wrote concurrency per kind, but a pool is shared by several kinds, so
  concurrency is per **pool** (`VEKTRA_ASSESS_POOL_<POOL>_CONCURRENCY`, the pre-flight pool also answers to
  `VEKTRA_ASSESS_PREFLIGHT_CONCURRENCY`) and budget, lease and attempts are per **kind**
  (`VEKTRA_ASSESS_JOB_<KIND>_*`). Loading is strict (`worker/policy.py`): a lease under twice the budget, a
  non-number or a misspelt name raises before anything is claimed. The `setup_check` kind gets its own pool
  (120 s) as the carried-over note asks; `preflight` is declared as a pool with no kind, because its kind and
  handler come with plan session-lifecycle.
- Single replica for the pilot; the advisory locks and fencing make an accidental second replica safe,
  not supported.
