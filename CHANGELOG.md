## [Unreleased]

### Changed

- **assess** (live E2E follow-up, 2026-11-13): a discussion turn the model provider refuses for the deployment's configuration no longer leaves the student's clock running. The configuration is an `auth_error` (a missing or refused key), always, or another non-429 4xx (a wrong model, a rejected parameter) only when a turn-shaped probe call (the outage probe's) is refused too; a 4xx the probe does not get belongs to that one request (a context-length or content-policy 400) and keeps the old path: the marked turn, `provider_refused`, the session ACTIVE, no outage (REQ-086), so such refusals never close a session. The probe is built and called only for such a 4xx, within at most 10 s and never past the reply's deadline + grace (a Start: its remaining budget and the budget the job runtime enforces, `VEKTRA_ASSESS_JOB_PREFLIGHT_BUDGET_S` included); out of time, or failing in any other way, it confirms nothing and the plain refusal stands. A confirmed one still ends with the marked "[risposta interrotta]" (now `reply_interrupted` `reason: service_misconfigured`, was `provider_refused`) and, in the same transaction (the student can never write in between), the session enters OUTAGE with that reason; when the database refuses the marker (no reply owed any more) nothing is paused. In OUTAGE the timer is frozen, the worker's probe keeps checking, and once the configuration is fixed the interval is credited exactly like a provider outage (G, the cap C and the 3-consecutive-failures rule included; left unfixed, C closes the session `service_failure`). The refused turn is not replayed. The operator still gets one `provider_config_refused` mail per site, cause and hour (its text now says the time is paused); a paused session sends no further turn. Every config refusal, confirmed or not, still alerts the operator as before. A Start refused for the configuration (the same rule: auth, or a 4xx the probe gets too) now rolls back `service_misconfigured` (was `provider_unavailable`): a system rollback (3-rollback notice, Start breaker), a new value of the `vektra_assess_start_rollbacks` `reason` label. Additive for the plugin: it never sees either reason.
- **assess** (teacher routes): a refusal that a refresh of the LMS facts may lift says when to retry, in one place: `error.details.retry_after_s` (integer, at most 5, today 3) and the `Retry-After` header. Carried by `403 ERR-ASSESS-021` `*_check_stale`, `409 ERR-ASSESS-024` `gate_inputs_stale`, and a `400 ERR-ASSESS-022` from `PUT .../config` whose field errors are all LMS facts (`assignment_without_cutoff`, `quiz_without_close_date`, `team_submission`, `marking_guide`, `lms_rubric_missing`, `lms_facts_unreadable`; on `available_until`, `opening_unknown` with no close date cached and `not_after_opening` against an opening from the cached close date): that refusal now queues a refresh of the facts (live symptom: enabling right after setting the cut-off was refused on the cached fact). Vektra cannot know when the LMS changed, so these refusals always carry the hint and are never declared final by the server: **the hint repeats, clients must retry at most once** and then show the refusal. The refresh is queued after the refusal in its own transaction; the hint is present only if that worked (otherwise the refusal comes back without it, never as a 500). The LMS load stays bounded by the job dedupe (per activity the refresh and one follow-up beside a pending, possibly running one). `not_an_editor` / `not_a_grader` and an end date before the teacher's attested opening carry no hint. Also carried by a `409 ERR-ASSESS-024` `gate` refusal decided on the student's cached render evaluation (a render check is queued) and by `PUT opening-fallback` refusals decided on the cached gate facts (`fallback_not_needed`, `close_unreadable`, `no_close_date`, `before_close`). A resolved activity is refreshed with the course and type Vektra resolved, never a request's hint; the worker never lets an unresolved read for another course replace resolved facts, and an older read does not replace a newer one on the database clock (a row dated past that clock, after a backward step, is always replaceable). Every cached row's age (teacher gate, render state, gate inputs) is read against `clock_timestamp()` with one rule: fresh from 5 s below zero (a row written a moment ago) up to the bound, a further negative age is a clock step and stale. A reset's render check gets the same single follow-up job as the teacher gate, and the render state and gate inputs are upserted with the same monotonic rule; the enrolment freshness also reads its age against `clock_timestamp()` but keeps any negative age fresh (its checks are inserted, never replaced, so a future-dated one must not refuse every turn). Fail closed is unchanged.

The hint "Ctrl+Invio per inviare" sits under the field (its own element, `aria-describedby` with the status line; `aria-keyshortcuts` on the field). A `local_vektradiscuss` older than 0.2.0 is refused at mint (`POST /api/v1/assess/tokens`) with `403 ERR-ASSESS-016`, so no student can open a discussion through it; its transcript calls are refused too, with `400 ERR-ASSESS-014` (`missing:cmid`; see the transcript routes entry under Added, below). ### Added

- **assess**: `POST /api/v1/assess/activities/{cmid}/gate-refresh` (`assess:teacher` key, body `{actor_userid, courseid, activity_type}`, `202 {cmid, queued, refreshed_at}`): the plugin calls it when a teacher page opens (Discussioni list, activity settings, grader page) so the activity's LMS facts are read again before the teacher's first action (live symptom: the first click after a few idle minutes was refused "checking your role"). Verifies nobody, returns no fact, coalesced per cmid (nothing queued while one is pending or when the activity's facts were read less than 10 s ago; a resolved activity is refreshed with its own course, whatever `courseid` the body says); any failure is safe to ignore. `GET /api/v1/assess/sessions/{sid}` adds `outage_reason` (`provider_unavailable` | `service_misconfigured`) in OUTAGE, and `outage_start` / the stream's OUTAGE `state` snapshot carry the same `reason`. No schema change.

Every activity of the export key's site where the subject has any row the subject erasure deletes, or a retention tombstone it rewrites, with: the sessions (`session_no`, `state`, `close_reason`, `created_at`, `deadline_at`, `closed_at`; `transcript_id` when it has a transcript, else its decrypted `turns` while live, `[]` while starting, and `null` with `turns_unavailable` (`transcript_pending`, `transcript_failed`, `transcript_purged`, `transcript_missing`) once closed without a transcript), the resets (`after_session_no`, `granted_at`, `consumed_at`), `extra_seconds` and `extra_granted_at`, `purged_sessions`, `technical_records` (row counts of the technical tables, never their contents) and `course_id` (the session's hint, else the latest mint's). Each subject table declares how it is exported (`privacy.subject.SUBJECT_EXPORT`, next to the erasure's `SUBJECT_TABLES`); a schema-scan test fails on a subject table nobody declared. One snapshot per page (REPEATABLE READ, read-only). Same key, site binding, paging (`X-Assess-Cursor` / `next_cursor`, 10 activities per page), errors and `Cache-Control: no-store` as the transcript export, whose audit row now carries `kind: transcripts`. Reset reasons, teacher notes and the grader who granted extra time are left out (an open DPO question under OQ-020). **Upgrade:** assess revision `a0004` adds indexes on `assess_token_jti` and `assess_render_checks` `(site_id, student_userid, cmid)` and the SECURITY DEFINER function `assess_transcript_job_states` (EXECUTE for the API role, which cannot read `assess_jobs`); run `alembic upgrade assess@head`.
- **assess**: an erasure that does not complete alerts the operator (OQ-033: the LMS's privacy API cannot leave its own request failed, so Vektra closes the loop). One `operator_notify` per request and event: `erasure_verification_failed` when a run records the request `failed` (in that transaction; a run that finds the request already completed by another records and sends nothing); `erasure_overdue` when it is still not completed `VEKTRA_ASSESS_ERASURE_ALERT_AFTER_S` (new, default 3600, 900-43200) after it was made, from the worker's `delivery_retry` tick, marked on the request (`assess_erasure_records.overdue_alerted_at`, assess revision `a0003`) so pruned job rows never bring a second email, and dropped at send time only if the request has since been erased; `erasure_abandoned` when the daily purge records a day-old open request `failed` (`abandoned`). The job and the email carry the site id, the request id and the scope only: no user id, subject hash or activity. A failure of the overdue sweep is logged (`assess_erasure_overdue_sweep_failed`) and the rest of the tick runs. The erasure and purge alert lines carry `erasure_id`, `erasure_scope` and `tables_left` (rows left per table, from the erasure's own table list only; allowlisted log keys), and a failed request keeps the same counts in `assess_erasure_records.rows_deleted->'left'`; `docker-compose.assess.yml` forwards `VEKTRA_ASSESS_ERASURE_ALERT_AFTER_S` and `VEKTRA_ASSESS_STORE_TRACES` to the worker. **Upgrade:** run `alembic upgrade assess@head` (revision `a0003` adds the column and a partial index). Operator guide: [erasure alerts](docs/guides/operators/assess-deployment.md#erasure-alerts).
- **assess**: the transcript routes take the plugin page's activity (plugin request). `POST /api/v1/assess/transcripts/{tid}/download-token` (both paths) and the grader's `POST /api/v1/assess/transcripts/{tid}/resend` take a **required** `cmid` (1 to 2^53-1, an integer or its decimal string, the same rule as `POST /tokens`; anything else is `400 ERR-ASSESS-014`, and a call without it is `400 ERR-ASSESS-014` with `details.reason` `missing:cmid`). When the transcript, or a purged transcript's tombstone, belongs to another activity, the request gets the envelope of an unknown transcript (`404 ERR-ASSESS-017`), before the role checks and the owner's `410`, audited `assess_ownership_mismatch_rejected` (`transcript_download_token_cmid` / `transcript_resend_cmid`, with role, key id, `sub` or `actor_userid` and the cmid). It closes the gap between the plugin, which checks the capability on its page's cmid, and Vektra, which checks the grader role on the transcript's activity. It does not hide whether a transcript exists: within the same activity a non-grader still gets 403 where an unknown id gets 404 (a possible follow-up). `local_vektradiscuss` 0.2.0, the new minimum (Changed, above), sends `cmid` on all three calls; an explicit `null` is `int_type:cmid` on every route, and the grader's resend validates its body before charging the rate limit; the interim counter of grader calls without it (`vektra_assess_transcript_cmid_missing_total`) and its log line `assess.transcript.cmid_missing` were removed when it became required.

On a managed or otherwise external Postgres that user normally cannot create roles, and the container does not start until the roles exist (the migration error names them and the attributes to create them with). That combination was tested on PostgreSQL 16 with a migration user that is neither superuser nor `CREATEROLE`, owns its database, and has the `vector` and `pgcrypto` extensions created for it, migrated up to the current head (`vektra-assess/tests/integration/test_migration_managed_postgres.py`, which also proves the platform branch alone needs none of it); a provider whose administrator lacks some of those rights is not covered by that test. `deploy/postgres/init.sql` no longer creates the assess roles.

### Added

- **learn**: student-owned conversation history that survives the browser (FEAT-027). Conversations are bound to the JWT `sub` — the LMS user the dashboard token was issued for — so history is no longer tied to the `sessionStorage` entry of one tab: `GET /api/v1/learn/conversations` lists the caller's own conversations for the course (metadata only, most recent first, soft-deleted ones excluded), and the widget resumes from it when the tab has no stored id, which is the case on every new device, browser or reopened window. `DELETE /api/v1/learn/conversations/{id}` lets a student erase one of their own conversations (soft delete, REQ-057), answering `404` for a conversation that does not exist, is already deleted, *or* belongs to someone else — the same answer on purpose, so the endpoint cannot be used to discover which conversation ids exist. The widget gains a two-step delete control (first click arms it, second within 5s deletes) and remembers a "new chat" for the tab, so the server-side resume does not undo the student's decision on the next load. A deletion removes that one conversation only: an older one is still offered on the next load, and course-wide erasure would need a bulk endpoint. All of it requires the persistent store: with `VEKTRA_CONVERSATION_KEY` unset the endpoints answer `ERR-LEARN-001` rather than reporting an empty history, because "you have no conversations" and "conversations are not being stored" are different statements. `docs/reference/configuration.md` documents the key, its one-way nature (it cannot be rotated in place without losing existing turns) and the fact that enabling it starts storing personal data.
- **ingest/rag**: material can now be ingested for retrieval without ever being cited (FEAT-026). `POST /api/v1/ingest` and `POST /api/v1/ingest/batch` accept an optional `metadata` form field — a flat JSON object merged into every chunk of the document, validated with `ERR-INGEST-005` (object only, scalar values, keys `[a-z][a-z0-9_]{0,63}`, 4 KB max) and carried through all three ingestion paths (sync, arq job, in-process fallback). One key is reserved: `hidden_from_students: true` keeps the content fully retrievable — it is embedded, searched, reranked, expanded and placed in the prompt exactly like any other chunk — while its **source is withheld from the response**. That covers the case the university deployment actually has: publisher material a student may read *through* the assistant, but which the assistant must not attribute or hand back as a citable document. The filter sits in the source-assembly step of both pipelines and on both their paths (four sites: `SimpleQueryPipeline` and `AdvancedQueryPipeline`, sync and SSE), never in retrieval, so relevance and grounding are unchanged. It applies to every caller including admin-scope keys — a rendering flag the client is asked to respect (the FEAT-014 pattern) would leave snippets and filenames sitting in a JSON body the browser can read. Withheld titles never appear. Keep evaluation mode off, and set `VEKTRA_ENV=production`, on any deployment students reach: the eval-mode guard only fires in production. With FEAT-021 citations on, withheld chunks reach the model carrying `citable="false"`, no `title` and **no `id`**: the context numbers only the sources the response actually carries, so a marker cannot address a withheld chunk and `[n]` still means `sources[n-1]` — the mapping the widget relies on. Numbering every chunk instead (the first shape of this) both leaked the existence of a withheld source and shifted every id after it, so the model's `[2]` addressed a source the client never received. `QueryTrace` records `sources_withheld` on the `document_names` step. The reserved key must be a JSON boolean: `"true"` is rejected rather than coerced, because `"false"` is truthy in Python and a coercing parser would hide every source in a namespace on a quoting mistake. Note for automation: metadata is not updated by re-ingesting an unchanged file (deduplication returns `exists`/`alias` without touching stored chunks), so flipping visibility requires `DELETE /api/v1/documents/{id}` followed by a fresh ingest; a content change needs no delete, since that path rewrites the chunks with the new request's metadata. The prompt templates changed, so `prompt_version` moves even for namespaces that never use the flag (trace comparability note, as in FEAT-021).

- **ci**: `vektra-shared/tests/test_image_content_boundary.py` fails when either convention that keeps secrets out of the image regresses (INFRA-008). The images are pushed automatically on every `v*` tag to a **public** package whose visibility cannot be reverted, so the two things standing between a working-tree secret and the world were a Dockerfile that copies named paths rather than the context root, and the `.dockerignore` rules above — both conventions, neither checked. The guard parses the Dockerfile (line continuations, comments, the `COPY ["a", "b"]` form, and `--from=` instructions skipped because they read a build stage rather than the context), keeps the sources that are real directories, and asserts `.dockerignore` excludes every forbidden name inside each of them. The gap was live only because BUG-023 was fixed: while reindex wrote nothing, there was never an old version to clean up. `VectorStoreProvider` grows `delete_index_version(namespace, index_version)`, implemented by both Qdrant and pgvector, and `scripts/reindex.sh --cleanup OLD_VERSION [NAMESPACE]` drives it. **The store refuses to delete the version it is currently serving** (409, `ERR-INDEX-001`), because the failure mode that matters here is not "an old version survives" but "the live index is emptied": the hand-written delete this replaces has no idea which version is live and is run at precisely the moment the operator is least sure. Verified against the live Qdrant stack: reindexing a namespace to v2 doubled it (12 → 24 points), the switch left search byte-identical, the cleanup reclaimed exactly the 12 old points, deleting the *active* version was refused, and the six other namespaces — all sitting at version 1 — lost nothing.

### Removed

- **config**: `VEKTRA_PARENT_CHILD_LEVELS` is removed (DEBT-027). It was validated (`>= 1` required with `VEKTRA_CHUNKING_STRATEGY=dual`) but read by nothing: `DualStrategyChunking` builds exactly two levels (parent + child), hardcoded, and the two-level shape is a structural assumption of everything downstream — the data model carries a single `parent_id` reference, both vector store providers filter retrieval on a binary `chunk_level`, and parent expansion (FEAT-017) is a single hop. The name promised a configurable depth that never existed (same class as DEBT-013), and the setting was worse than inert: the validator made `dual` chunking **fail to boot** unless this do-nothing variable was set. `chunking_strategy=dual` now works without it. - **config**: `VEKTRA_RERANK_TOP_K` is removed (DEBT-013). It promised "final top-k results after reranking" — which is exactly what the request's `top_k` already does: `AdvancedQueryPipeline` passes `query.top_k` (HTTP body, default 5) as the reranker's cut, and nothing ever read the config field. Defined, validated, tested, documented, wired to nothing — the same class as `VEKTRA_PARENT_CHILD_LEVELS` above. Wiring it instead of removing it was rejected on purpose: demoting the request's `top_k` to "how many sources come back" would break the invariant that `sources` are exactly the chunks the LLM saw (or just duplicate `query.top_k`), and using the config as a silent `min()` cap would truncate a client's request with a `200` and no signal — the reassuring-lie failure mode this repo keeps relearning. The post-rerank cut is legitimately per-request; server-side quality is guarded by the relevance threshold, the rescue (TECH-007) and the funnel width, which is what actually became configurable (see Added). Deployments with the variable set — the Combo D recipe included `VEKTRA_RERANK_TOP_K=5` — are unaffected (`RerankConfig` ignores unknown env vars) but should drop it from their `.env`: the value it carried, `5`, is what the request default does anyway.

- **index**: in Qdrant mode, every code path that read chunk text from Postgres worked on an empty table and reported success (BUG-023, [ADR-0026](.s2s/decisions/ADR-0026-document-chunks-pgvector-internal.md)). `document_chunks` is written only by the pgvector provider, so with `VEKTRA_VECTOR_STORE_PROVIDER=qdrant` — the configuration every real deployment runs — it holds nothing, and the paths that queried it did not fail, they lied: `reindex` re-embedded no chunks and reported `completed` (the root cause of the no-op previously attributed to BUG-021), `GET /stats` reported `chunk_count: 0` for populated namespaces, `POST /documents/{id}/chunks` wrote to the *inactive* store, `GET /health` reported the index healthy while the store backing it was unreachable, and — the serious one — `DELETE /documents/{id}` returned `200 {"chunks_removed": 0}`, soft-deleted the Postgres row, left the Qdrant points in place, and **the deleted document went on answering queries**. Retention (REQ-057) had the same defect and was worse: it hard-deleted the document row and relied on the `document_chunks` CASCADE, leaving the content in Qdrant, still searchable and no longer traceable to any document. All of these now go through the `VectorStoreProvider` Protocol, which grows `list_chunks()` and `count_chunks()` and an optional `index_version` on `store()`; `document_chunks` is now formally private to the pgvector provider. A reindex over a non-empty namespace that stores nothing fails loudly instead of reporting `completed`. Verified against the live Qdrant stack: reindex rewrites the collection (measured 0 → 12 points on the target version, source version preserved), stats match the real point counts, and a deleted document is no longer retrievable.
- **index**: `QdrantVectorStoreProvider.retrieve()` now scopes by `index_version` like search and like the pgvector provider, so a chunk from a stale index version is no longer reachable through parent expansion (FEAT-017) when search itself could never return it.
- **index**: `QdrantVectorStoreProvider.delete()` returns the number of points it removed instead of a hardcoded `0`; that placeholder is what let `DELETE` report `chunks_removed: 0` while it was in fact removing nothing.
- **ci**: the integration suite now runs as a matrix against **both** vector stores (`pgvector` and `qdrant`). It ran against pgvector only, which is why this entire class of bug survived for months: the sole Qdrant test mocked the `qdrant_client` module wholesale, and a mocked client cannot notice that a table is empty. `tests/integration/test_chunk_lifecycle.py` asserts the chunk lifecycle through the public API on whichever store is active, including that a deleted document is not retrievable.

### Security

- **api**: `top_k` on `POST /api/v1/query` and `POST /api/v1/learn/query` is now bounded `1..100`, the same validation `POST /api/v1/search` has always carried (BUG-026). Both request bodies typed it as a bare `int = 5` with no bounds, and the pipeline computes the retrieval fetch as `max(query.top_k, rerank.fetch_k)` — so any query-scope key sending `top_k=100000` drove a 100000-candidate vector search *and* a cross-encoder scoring pass over all of them, CPU-bound work per request that rate limiting caps only by count, not by cost. Non-positive values were accepted too: with reranking on, `top_k=0` or negative produced an empty post-rerank list and the query answered `200 no_relevant_context` — a request that lies about why it found nothing — instead of failing validation. Both fields are now `Field(5, ge=1, le=100)`; out of range is an explicit `422`, not a silent `min()` cap (the reassuring-lie failure mode rejected for the same endpoint in DEBT-013). The `422` is FastAPI's standard `RequestValidationError` shape (`{"detail": [...]}`), not the REQ-010 envelope — matching what `/search`'s own `le=100` already returns, since the envelope handler only unwraps `HTTPException`-raised errors and no `RequestValidationError` handler is registered. Pre-existing, not introduced by DEBT-013: the `max()` funnel was already there; #117 only made its constant configurable. Verified live before the fix (`/query` accepted `top_k=200` with `200`, and `top_k=0` returned `200 no_relevant_context`); `docs/reference/api.md` documents the `1-100` range on both endpoints.
- **index**: `DELETE /api/v1/documents/{document_id}` now enforces namespace binding (H5). It took the namespace straight from the query string and never checked it against the key's binding, so an admin key bound to one namespace could name another and have it honoured. The gap predates this release, but it was survivable only while the delete was a no-op against the active vector store: now that the delete actually removes the chunks (BUG-023, above), the same request would be a real cross-namespace deletion. The new `GET /documents/{id}/chunks` had the mirror-image defect — `namespace` defaulted to the literal `"default"`, so a namespace-bound key that omitted the parameter was rejected on its own documents — and both endpoints now resolve the namespace from the key binding, as `/stats` and `/search` already did. The 403 returns the `ERR-AUTH-003` envelope instead of a bare string. Found in review.
- **index**: `check_provider_registration` (ARCH-057 step 5) is now actually called at startup, and checks the `embedding`/`default` alias instead of a hardcoded `sentence-transformers` name. The function was dead code — nothing called it outside its own unit test — which is why TEI mode (`VEKTRA_EMBEDDING_PROVIDER=tei`) started fine even though the check could never see its provider. Found in review.
- **docker**: the Qdrant healthcheck (`docker-compose.yml`, `qdrant` service) shelled out to `curl`, which the `qdrant/qdrant` image does not ship, so the container was permanently reported `unhealthy` in every deployment using the `qdrant` profile. Replaced with a `bash`-only check against `/healthz` over `/dev/tcp`, verified against the pinned `v1.17.0` image (empirically confirmed to flip the live container from `unhealthy` to `healthy`). The TEI healthcheck was also audited and does ship `curl`, so it is unchanged.
- **docs**: corrected two claims that were false for the default Qdrant deployment. The ingest API reference documented the sync response `status` as `"indexed"` (the code returns `new`, `exists` or `alias`; `indexed` is an *async job* status) and omitted Markdown from the supported formats, although `MarkdownExtractor` has been registered for `text/markdown` all along. The agent instructions (`.claude/CLAUDE.md`) claimed chunk text lives in the Postgres `document_chunks` table: that table is written only by the pgvector provider, so in Qdrant mode it is empty and Qdrant's payload is the sole source of chunk text — which is also the root cause of the `reindex` no-op tracked under BUG-021.
- **docker**: `CMD_TARGET=migrate docker run <image>` (the env-var invocation form) now actually runs the one-shot migration instead of silently booting a full server. The Dockerfile's `CMD ["server"]` was always passed as `$1` to the entrypoint, which the precedence chain favors over the `CMD_TARGET` env var, so the documented env-var form never worked — this hung a production deployment script waiting on a server that was never going to migrate. Removed the Dockerfile `CMD` (the entrypoint already defaults to `server` with no argument); `docker run <image> migrate` continues to work unchanged.
- **tests** (index): `test_pgvector_unit.py`'s parent-chunk tests now exercise the real `DocumentChunkOrm` class via a `session.add` intercept instead of mocking the ORM class and asserting on its constructor call args, per `.coderabbit.yaml`'s instruction to never mock SQLAlchemy ORM classes.
- **app**: the stack failed to start whenever `VEKTRA_SPARSE_EMBEDDING_PROVIDER` was set, so hybrid search could not be enabled at all (BUG-024). Startup validation looks the sparse provider up by its configured name (`fastembed-bm25`), but the app registered it only under `"default"` — the vector store registers both aliases, the sparse provider registered one — so the check that was wired up in the previous release killed every stack with sparse embeddings on. The alias is now registered. The reason nothing caught it is worth recording: `vektra-app/tests/` was run by **nothing**, neither `make test` nor CI, although it covers the module that wires every provider together, and the existing check tests hand `check_provider_registration` a mock registry that already contains the name, asserting the check against a fiction. The app suite now runs in `make test` and in a new `test-app` CI job, and `test_provider_registration.py` wires the real registration step to the real check.

### Added

- **rag**: optional retrieval-filter rescue for multi-part questions (TECH-007, `VEKTRA_RETRIEVAL_RESCUE_TOP_K` + `VEKTRA_RETRIEVAL_RESCUE_FLOOR`, default off). When `VEKTRA_MIN_RELEVANCE_SCORE` empties the candidate set, keep the top-N chunks above an absolute floor instead of refusing: the cross-encoder scores each partial-answer chunk of a comparative/multi-part question below the threshold (it answers only one part), so on the eval corpus 9/10 multi-chunk questions died at the filter with `before=5 after=0` despite 90% raw retrieval hit. With the rescue, borderline sets reach the LLM, which arbitrates via strict grounding. The `retrieval_filter` trace step now records a `rescued` count.
- **rag**: optional per-namespace inline source citations (FEAT-021, `citations_enabled` in the namespace config JSONB via `PATCH /api/v1/admin/namespaces/{id}/config`, default off, advanced pipeline only). When enabled, the system prompt instructs the LLM to add inline `[n]` markers matching the `<source id>` elements, the context template carries a `title` attribute ("filename, p.N"), and each returned source includes a `title` field; the learn widget renders the markers as superscripts with a tooltip. Default-off renders byte-identical prompts; `prompt_version` changes anyway because the template files changed (trace comparability note).
- **rag**: optional parent chunk expansion in the advanced query pipeline (FEAT-017, `VEKTRA_PARENT_EXPANSION_ENABLED`, default off). With `VEKTRA_CHUNKING_STRATEGY=dual`, retrieved child chunks are replaced with their parent chunk's text after the retrieval filter and before token budgeting; children of the same parent collapse into the highest-scored one. Parent-child linkage is now actually persisted (deterministic `uuid5(doc_id, position)` ids, `parent_id` in the Qdrant payload and in the pgvector column), a new `VectorStoreProvider.retrieve()` fetches chunks by id, and the trace records `children_expanded`/`siblings_merged`/`parents_fetched` in a `parent_expansion` step.

### Changed

- **index**: vector search now excludes parent-level chunks (`chunk_level=parent`) in both providers; parents are context material fetched by id during expansion, not retrieval targets. Only affects documents ingested with `dual` chunking, whose parents previously polluted search results.
- **index**: pgvector `store()` honors caller-provided UUID chunk ids (deterministic ids from ingest) instead of always generating random ones; non-UUID ids still fall back to random.

### Fixed

- **docker**: the `INSTALL_UNSTRUCTURED=true` image variant builds again (BUG-022). torchvision (transitive via unstructured-inference) resolved from PyPI with CUDA-built wheels while torch is pinned to the CPU index, crashing the build with `operator torchvision::nms does not exist`. - **index**: `/api/v1/search` now resolves the embedding, sparse-embedding, and vector-store providers from the ProviderRegistry instead of hardcoding pgvector and reading a never-populated `app.state` attribute (BUG-021). In Qdrant deployments the endpoint returned zero results (it searched the empty `document_chunks` table) and hybrid mode always fell back to dense; the RAG pipeline (`/api/v1/query`) was unaffected. Found by the Sprint 3 baseline `make eval-retrieval` run.
- **tests**: unit tests are now hermetic against the developer's local `.env` (DEBT-025). Importing litellm during pytest collection loads `.env` into the process environment, which made 4 default-assertion tests in `vektra-shared` fail on dev machines while CI stayed green. An autouse fixture in `vektra-shared/tests/conftest.py` scrubs ambient `VEKTRA_*` variables; production settings loading is unchanged. The fixture is replicated in `vektra-core` and `vektra-ingest` (FEAT-017 surfaced the same leak there: ambient `VEKTRA_CHUNKING_STRATEGY=dual` broke 12 chunker and pipeline-default tests).

## [0.1.0] - 2026-02-27

Phase 1 MVP: from `git clone` to first RAG query in under 30 minutes.

### Added

- **vektra-shared**: 9 Protocol interfaces, configuration (40 env vars), API key auth with argon2id, ProviderRegistry, startup validation
- **vektra-core**: RAG query pipeline (embed, search, filter, prompt, LLM), multi-turn conversations, streaming SSE, LLM graceful degradation (primary + fallback), token budget allocation
- **vektra-ingest**: PDF extraction via pdfplumber, fixed-size chunking, async jobs for large files (>10 MB), duplicate detection (SHA-256), content type validation via python-magic
- **vektra-index**: pgvector-backed semantic search, embedding generation (all-MiniLM-L6-v2), namespace isolation, relevance threshold filtering, overlap deduplication
- **vektra-admin**: API key CRUD, hierarchical health endpoints (/health, /health/{component}, /health/memory), audit logging, Prometheus metrics on /metrics
- **Docker Compose stack**: single-command deployment (vektra + postgres), optional Ollama profile for local LLM
- **CI pipeline**: GitHub Actions (lint, unit tests x5 components, integration tests, NFR hard gates, shell script validation, auto-labeler)
- **Makefile**: 10 operator targets (test, lint, health, demo, etc.)
- **Operator scripts**: health.sh, create-key.sh, ingest.sh, query.sh, demo.sh
- **Documentation**: Diataxis structure (getting started, API reference, configuration, error codes, architecture overview, contributor guide, n8n workflow)
- **13 error codes**: structured error envelope (ERR-AUTH, ERR-INGEST, ERR-QUERY, ERR-CONFIG) with categories and remediation
- **23 ADRs**: architectural decisions from modular monolith strategy to query pipeline design
