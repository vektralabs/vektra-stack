# Assess keys: backup, restore drill and rotation

Operator runbook for the assessment discussion feature (`VEKTRA_ASSESS_ENABLED=true`). Key
purposes and the rotation order are in [configuration](../reference/configuration.md#assess-key-purposes-and-rotation).

## File ownership on Linux

The assess containers run as uid 1000 and refuse a secret file owned by any other user (or not by
root), or with a mode looser than 0440. Docker Compose on a Linux engine does not remap the owner of
a file secret, so after `make assess-keys` run `sudo chown -R 1000:1000 secrets/assess` (Docker
Desktop on macOS maps ownership for you). The CI job does exactly this.

## Key inventory

Every assess secret, the process that holds it, and what losing it costs. "Lost" means no copy of
the key survives anywhere; a key that is only missing from one container is a configuration
error, caught at startup by the key matrix.

| Secret | Held by | Referenced in the database | If it is lost |
|---|---|---|---|
| `assess_kek` | worker | `assess_session_keys.kek_kid` | every session's snapshot and turns are unreadable, for good |
| `assess_transcript_kek` | API and worker | `assess_transcripts.transcript_kid`, the reasons' `reason_kid` | every transcript and every teacher reset or termination reason is unreadable |
| `assess_teacher_config_private` (+ `_public` on the API) | worker | `assess_activity_config_sealed.kid` | the sealed solutions and rubrics cannot be opened: teachers must enter them again |
| `assess_handoff_private` (API) / `assess_handoff_public` (worker) | API / worker | `assess_session_handoff.handoff_kid` | the LIVE sessions cannot continue; closed sessions are unaffected (their hand-off is deleted at close) |
| `assess_token_signing` | API | none (tokens live minutes) | every outstanding token is refused; replace it and the plugin mints new ones |
| `assess_ws_tokens` | worker | none | the worker cannot read the LMS; replace the tokens |
| `assess_smtp` | worker | none | no email until the relay credentials are replaced |
| `assess_db_api_password` / `assess_db_worker_password` | API / worker | none | reset the role password in Postgres and replace the file |

There is no subject-key secret: the subject reference of a tombstone or an erasure is an unkeyed
`sha256(site|userid)`, so export and erasure keep working whatever happens to the keys above.

## Check the keys against the database

After a restore, after a key change, and whenever a container was rebuilt from backed-up
secrets, run the check in BOTH containers:

```bash
docker compose -f docker-compose.yml -f docker-compose.assess.yml --profile assess \
  exec vektra-assess-worker python -m vektra_assess.keys verify --role worker
docker compose -f docker-compose.yml -f docker-compose.assess.yml --profile assess \
  exec vektra python -m vektra_assess.keys verify --role api
```

For every key the role holds it reads the key ids the database references and tries to open one
row per id. It prints each keyring's kids with a short fingerprint (`sha256(key)[:12]`, never the
key) so two deployments can be compared, then one line per check:

- `MISMATCH ... (kid_not_loaded)`: the rows name a kid the keyring does not hold;
- `MISMATCH ... (wrong_key:InvalidTag)`: the kid is there, but its bytes are not the ones the rows
  were written with: the keys come from another deployment or another backup;
- `skipped ... (not_readable)`: this role may not read those rows. For the hand-off key no
  container checks them: the API holds `assess_handoff_private` but may not read
  `assess_session_handoff`, and the worker can read the table but never holds the private key.

Not every key is checked the same way. The check OPENS a row for `assess_kek` (a session DEK),
`assess_transcript_kek` (a transcript, and the reset and termination reasons): a wrong key under
the right kid is caught (`wrong_key`). For `assess_teacher_config_private` (worker) it confirms
only that every referenced kid is present (`kid_present`): same-named keys with other bytes pass.
The hand-off pair (`assess_handoff_private` on the API, reported `skipped`, and
`assess_handoff_public` on the worker), `assess_teacher_config_public` (API) and
`assess_token_signing` are checked by fingerprint only. So exit 0 proves the
session and transcript keys; for the others compare the printed fingerprints with the backup's.

Exit code 0 means every referenced key opened its rows, 1 means at least one mismatch, 2 means the
check could not run (settings, secrets or database). Treat 1 as an incident before the stack serves
anyone: nothing else fails until a teacher opens a transcript.

## Back up the keys, separately from the database

The database holds only ciphertext. The keys that open it live in `secrets/assess/` (generated by
`make assess-keys`). Back the directory up **offline and apart from every database dump**: a dump
plus the keys is the whole exam record, so the two must never travel together, be stored on the
same medium, or be readable by the same account.

**A lost `assess_kek` means every snapshot and turn of every session is unrecoverable.** There is
no fallback and no second copy in the database. The same is true, for transcripts and the
teachers' reasons, of `assess_transcript_kek`, and for teacher configuration, of
`assess_teacher_config_private`.

What to back up, and when:

1. **The whole `secrets/assess/` directory**, after `make assess-keys` and again after every change
   to any file in it (a rotation step, a new site's WS token, a new SMTP account). A backup taken
   in the middle of a rotation must contain both the old and the new kid.
2. **The fingerprints**, next to each key backup: the output of
   `python -m vektra_assess.keys verify` in both containers (it prints, per keyring, every kid with
   `sha256(key)[:12]`, never the key). The restore drill compares against them.
3. **Retired kids**, in the offline backup only, until the cadence in
   [key rotation](#cadence-rotation-retirement-and-backup-retention) allows destroying them.
   Superseded copies of a keyring that hold nothing the current backup lacks may be destroyed.

The database dump itself is taken with the standard PostgreSQL tools (for example
`pg_dump -Fc`) under your own backup policy; its retention is what
`VEKTRA_ASSESS_DB_BACKUP_RETENTION_DAYS` must state.

## Restore drill

A key backup that was never restored is not a backup. The drill proves, on a host that never ran
the deployment, that a database dump and the separately kept keys together give back the exam
record, and that what was purged stays gone (ARCH-079). Run it before the pilot, then at least
every 30 days (the pilot go/no-go requires a drill within the last 30 days) and after every key
rotation.

**Status: no drill has been run yet.** It needs a clean host, which does not exist at the time of
writing. The procedure below is written from the code; the PostgreSQL dump and restore commands
are standard ones that no test in this repository runs.

### Before the backup: pick the evidence

On the production deployment, when you take the dump and the key backup you will restore:

1. Choose one **retained** transcript (its session CLOSED, not purged) and fetch it through the
   subject export, which returns the exact bytes the in-course download serves. It needs the
   site's `assess:privacy-export` key. The export is an exam record, so it goes to a private
   temporary file that is removed on success or failure:

   ```bash
   (
     umask 077
     export_file=$(mktemp) || exit 1
     trap 'rm -f -- "$export_file"' EXIT
     trap 'exit 1' HUP INT TERM
     curl -sf -H "Authorization: Bearer $EXPORT_KEY" \
       "https://vektra.uni.example/api/v1/assess/privacy/subjects/$USERID/transcripts" \
       > "$export_file" &&
     python3 -c 'import base64,hashlib,json,sys; d=json.load(open(sys.argv[1]))
   for i in d["items"]: print(i["transcript_id"], i["sha256"], hashlib.sha256(base64.b64decode(i["content_base64"])).hexdigest())' "$export_file"
   )
   ```

   Record the transcript id and the sha256 you computed (the third column; it must equal the
   second, the stored hash).
2. Take the dump and the drill's reference figures from **one database snapshot**, so the
   figures describe exactly what the dump contains. As the database owner, open a session and
   keep it open until step 3:

   ```sql
   BEGIN ISOLATION LEVEL REPEATABLE READ;
   SELECT pg_export_snapshot();   -- e.g. 00000003-0000001B-1
   ```

   In another shell, dump that snapshot:

   ```bash
   pg_dump -Fc --snapshot=00000003-0000001B-1 -d vektra -f vektra-drill.dump
   ```

3. Back in the open session (it still sees the exported snapshot), record:

   ```sql
   -- the number of sessions whose DEK the restore must give back
   SELECT count(*) FROM assess_session_keys WHERE kek_wrapped IS NOT NULL;
   -- a few purged sessions (tombstones) the restore must keep unrecoverable
   SELECT session_id FROM assess_purge_records ORDER BY purged_at DESC LIMIT 5;
   COMMIT;
   ```

   If `assess_purge_records` is empty, no purge has run yet: record that, and the
   "purged data stays unrecoverable" part of the drill cannot pass until a later drill.
4. Take the key backup (with the fingerprints) at the same time.

### On the clean host

Define the Compose command once in the shell you run the drill from:

```bash
compose() { docker compose -f docker-compose.yml -f docker-compose.assess.yml --profile assess "$@"; }
```

1. Use the same image version as the deployment that took the backup. Start Postgres alone on an
   empty volume (`compose up -d postgres`): its init script creates the extensions and the two
   assess roles (NOLOGIN).
2. Restore the dump as the database owner (`pg_restore -d vektra vektra-drill.dump`).
3. **Before any assess process starts** (the worker's purge and delivery ticks would change the
   data), check the dump against the figures of preparation step 3, as the database owner:

   ```sql
   -- must equal the count recorded from the snapshot
   SELECT count(*) FROM assess_session_keys WHERE kek_wrapped IS NOT NULL;
   -- every selected tombstone came back: must equal the number of ids you selected
   SELECT count(*) FROM assess_purge_records
    WHERE session_id IN ('<id 1>', '<id 2>', '<id 3>', '<id 4>', '<id 5>');
   ```

   Only when both match, check that the tombstoned sessions keep nothing that opens. Each
   query must return 0:

   ```sql
   -- no wrapped DEK survives for a tombstoned session
   SELECT count(*) FROM assess_session_keys k
     JOIN assess_purge_records p ON p.session_id = k.session_id
    WHERE k.kek_wrapped IS NOT NULL;
   -- no turn or snapshot ciphertext survives
   SELECT count(*) FROM assess_turns t JOIN assess_purge_records p ON p.session_id = t.session_id;
   SELECT count(*) FROM assess_snapshots s JOIN assess_purge_records p ON p.session_id = s.session_id;
   -- no transcript ciphertext or wrapped DEK survives
   SELECT count(*) FROM assess_transcripts t
     JOIN assess_purge_records p ON p.transcript_id = t.id
    WHERE t.ciphertext IS NOT NULL OR t.dek_wrapped IS NOT NULL;
   ```

   The tombstone check comes first because these joins return 0 just as well on a dump that
   holds no tombstones at all. They check the dump, not the keys: a purge removes the wrapped
   DEK, so the KEK cannot open the session whatever key set is mounted. A dump taken BEFORE a
   purge still holds the wrapped DEK; that is the backup-retention exposure described in the
   rotation cadence.
4. Put the backed-up `secrets/assess/` in place (owner uid 1000, mode `0400`). The drill host must
   not reach production systems: replace the restored `assess_ws_tokens` with `{}` (no LMS call
   can succeed) and point `VEKTRA_ASSESS_SMTP_HOST`, `assess_smtp` and
   `VEKTRA_ASSESS_OPERATOR_EMAIL` at a mail sink, so a delivery still pending in the dump cannot
   mail a teacher. Neither credentials file is checked by `verify`. Then bring the stack up:
   `compose up -d`. `vektra-assess-db-init` sets the role passwords from the restored secret
   files, and the API's `alembic upgrade head` finds the schema already at its revision.
5. Verify the keys:

   ```bash
   compose exec vektra-assess-worker python -m vektra_assess.keys verify --role worker; echo "exit $?"
   compose exec vektra python -m vektra_assess.keys verify --role api; echo "exit $?"
   ```

   Both must exit 0, and every printed fingerprint must equal the one recorded with the backup
   (the keys that `verify` lists but cannot open by a row: the hand-off pair,
   `assess_teacher_config_public` and `assess_token_signing`). `verify` opens one row per kid,
   not every row: a wrong key for some rows under a kid is found only when those rows are opened.
6. Fetch the chosen transcript again on the drill host, with the same export key (its row came
   back with the dump), the same way as in preparation step 1. Its sha256 must equal the value
   recorded before the backup. A `500 ERR-ASSESS-020` means the restored bytes do not decrypt or
   do not re-hash to the stored value: the drill failed.
7. Destroy the drill host's copies of the dump and the keys.

### Record the result

Record every drill in the pilot go/no-go document
([assess-pilot-go-no-go.md](operators/assess-pilot-go-no-go.md#restore-drill-record)): date,
operator, image version, dump and key backup identifiers, both `verify` exit codes, the
fingerprint comparison, the transcript id with both sha256 values, the snapshot count and the
restored count, the tombstone count and the four purge counts, and PASS or FAIL. A FAIL is an incident: the backup cannot be relied on until a drill passes.

## Key rotation

### How a rotation works

Every keyring holds several kids; each ciphertext records the kid it was written under, and new
data is always written under the `active` kid. A rotation therefore has four steps, and only the
middle one differs per key:

1. **Add** a new kid, deploy it to every process that holds the keyring, and make it `active`
   (for a keyring the API and the worker share, in two phases: see the transcript KEK).
2. **Move** the rows still under the old kid to the new one.
3. **Prove** that nothing references the old kid: the command exits 0 or the count query below
   returns 0, and `python -m vektra_assess.keys verify` exits 0 in both containers.
4. **Retire** the old kid from the live keyring, recreate, verify again. Keep the retired key in
   the offline backup until it may be destroyed (see the cadence below).

Every process loads its keyrings when it starts, so each "deploy" below means: replace the secret
file, then recreate the service (`compose up -d --force-recreate <service>`). Recreate, not
restart: Compose bind-mounts each secret file, and a replacement that writes a new file (an
editor's save, `mv`, `rm` and recreate) leaves a running or merely restarted container on the
old one. That holds for `assess_ws_tokens` too, although the worker re-reads it on every LMS
call.

**New key material.** There is no command that adds one kid to an existing keyring. Generate a
complete scratch set and take the value you need from it:

```bash
uv run python -m vektra_assess.keys generate --out /secure/scratch/assess-new
```

Every keyring in the scratch set holds one kid, `k1`. Copy its base64 value into the live file
under a NEW kid name (for example `k2`; any string except `purged`), keeping the old kid. For an
X25519 pair (`assess_handoff_*`, `assess_teacher_config_*`), take the private and the public value
from the same scratch set: they are generated as a matching pair. Then destroy the scratch set.
Editing a live keyring by hand is the step most likely to break a deployment: a JSON error or a
wrong mode stops the process at start (see [secrets](operators/assess-secrets.md#startup-refusals)),
so keep the previous file until `verify` has passed.

`compose` is the shell function defined in [the restore drill](#on-the-clean-host):

```bash
compose() { docker compose -f docker-compose.yml -f docker-compose.assess.yml --profile assess "$@"; }
```

### Session KEK (`assess_kek`, worker only)

1. Add `k2` to `assess_kek` with `"active": "k2"`, keep `k1`. Recreate the worker. New sessions
   are wrapped under `k2`.
2. Re-wrap the session DEKs still under `k1`:

   ```bash
   compose exec vektra-assess-worker python -m vektra_assess.keys rewrap --what session-keys --from-kid k1
   ```

   It runs as the worker role in committed batches (`--batch`, default 100) and prints only
   counts and kids. Exit 0: no row is left under `k1`. Exit 1: rows remain, either locked
   elsewhere (run it again) or rows that did not decrypt, listed by id (a data or key problem:
   investigate before going on). Exit 2: it could not run (settings, secrets, a kid the keyring
   does not hold, or `k1` still the active kid).
3. `compose exec vektra-assess-worker python -m vektra_assess.keys verify --role worker` exits 0.
4. Remove `k1` from the live `assess_kek`, recreate the worker, run `verify` again.

The hand-off rows of live sessions are sealed to the API's hand-off key, not wrapped under the
KEK, so a KEK rotation does not touch them. A purged or erased session has no wrapped DEK
(`kek_wrapped IS NULL`), so the re-wrap skips it and it stays unrecoverable.

### Transcript KEK (`assess_transcript_kek`, API and worker)

The API reads AND writes under this key (it opens transcripts for download and encrypts the
teachers' reset and termination reasons), so the new kid must be readable everywhere before
anything writes it:

1. Add `k2` as an INACTIVE kid (`"active"` stays `k1`) and deploy it to EVERY API instance and the
   worker.
2. Set `"active": "k2"` and deploy again everywhere, draining the old instances. Activating in one
   step would let an updated instance write a reason that a not yet updated one cannot read.
3. Re-wrap, from the worker:

   ```bash
   compose exec vektra-assess-worker python -m vektra_assess.keys rewrap --what transcripts --from-kid k1
   ```

   One command re-wraps the per-transcript DEKs (`crypto.rotation.rewrap_transcript_deks`) AND
   re-encrypts the teachers' reasons (`rewrap_teacher_reasons`, plan teacher-ops 11b), so the kid
   cannot be retired with reasons left behind. Same exit codes as above. It refuses to run while
   `k1` is still active (exit 2), which is why step 2 comes first.
4. `verify` exits 0 in the worker (`--role worker`) and in every API container (`--role api`).
5. Only now, once no process holding `k1` as active is left and the last run exited 0, remove `k1`
   from the live keyring and deploy everywhere.

A reason that no longer decrypts is shown as `reason: null`, `reason_state: "unreadable"` in the
teacher list (alert `teacher_reason_unreadable`): that is the symptom of a retired kid that still
had reasons under it.

### API hand-off key pair (`assess_handoff_private` on the API, `assess_handoff_public` on the worker)

The worker seals the DEK of each LIVE session to the API's hand-off public key (the active kid of
its `assess_handoff_public`); the API opens it with the private key named by the row's
`handoff_kid`. A hand-off row exists only while its session is ACTIVE or OUTAGE: the close
deletes it. So at most the live sessions (bounded by the admission limit K and the session
duration) carry an old kid, and they go away on their own.

1. Take a new pair from a scratch set. Add it as kid `h2` to `assess_handoff_private` on EVERY API
   instance (keep `h1`; the API opens by kid) and, where the API mounts it, to its
   `assess_handoff_public`. Recreate the API instances.
2. Add `h2` to the worker's `assess_handoff_public` with `"active": "h2"`. Recreate the worker. New
   hand-offs are sealed to `h2`.
3. Wait until no live session carries `h1`. As the database owner (neither assess role can be
   used: the API role may not read `assess_session_handoff`):

   ```sql
   SELECT count(*) FROM assess_session_handoff WHERE handoff_kid <> 'h2';
   ```

   The longest a session can stay live is its frozen duration (at most 240 minutes) plus its
   credited outage time (at most 15 minutes) plus the reply grace, so the count reaches 0 within
   a few hours; read the count, do not rely on the clock.
4. Remove `h1` from the API's keyring and recreate the API. Removing it earlier makes every live
   session under `h1` fail to load its material.

`crypto.rotation.reseal_handoffs(conn, kek_keyring, new_api_pub, new_kid)` re-seals the live rows
at once instead of waiting, but **no command wraps it**: it is a Python function, exercised only
by `vektra-assess/tests/integration/test_shred_rotation.py`. Waiting is the supported path.

### Teacher-config key pair (`assess_teacher_config_public` on the API, `_private` on the worker)

The API seals each write-only field (solution, pasted rubric, recipients) to the active kid of
`assess_teacher_config_public`; the worker opens it with the private key named in the blob.
Sealed fields stay until a teacher changes them, so waiting does not move them.

1. Take a new pair from a scratch set. Add the private key as `t2` to the worker's
   `assess_teacher_config_private` (keep `t1`) and recreate the worker.
2. Add the public key as `t2` with `"active": "t2"` to the API's `assess_teacher_config_public`
   (and to the worker's, where it is mounted). Recreate the API instances. New saves are sealed to
   `t2`.
3. Count the fields still sealed under another kid, as the database owner:

   ```sql
   SELECT count(*) FROM assess_activity_config_sealed WHERE sealed_blob IS NOT NULL AND kid <> 't2';
   ```

4. **Keep `t1` in the worker's private keyring while that count is above 0.**
   `crypto.rotation.reseal_teacher_configs(conn, old_worker_priv, new_worker_pub)` re-seals the
   rows, but no command wraps it (it is exercised only by the integration tests
   `test_shred_rotation.py` and `test_teacher_config_format.py`). Until one exists, a
   teacher-config rotation stops at step 3: the API seals new data to `t2`, the old blobs stay
   readable under `t1`, and `t1` cannot be retired. `verify --role worker` checks only that every
   referenced kid is present (`kid_present`).

### Token signing key (`assess_token_signing`, API only)

Tokens are signed with the active kid and verified against every kid the keyring holds; no token
is stored. With more than one API instance, roll it out in two phases like the transcript KEK
(an instance that does not hold the new kid refuses tokens signed with it):

1. Add `s2` as an inactive kid on every API instance and recreate them.
2. Set `"active": "s2"` everywhere and recreate.
3. Wait for the longest token lifetime: `VEKTRA_ASSESS_SESSION_TOKEN_TTL_S` (default 900 s; the
   pre-session and download tokens live at most 120 s).
4. Remove `s1` and recreate. A token still signed with `s1` is then refused with `401`; the plugin
   mints a new one (and `GET /sessions/{sid}` re-mints the session token on resume).

`verify` lists this keyring by fingerprint only: nothing in the database references it.

### Subject references (nothing to rotate)

There is no subject-key secret. The subject reference of a tombstone or an erasure is an unkeyed
`sha256(site|userid)`, and a recipient reference is `sha256(site|address)`. Nothing can be rotated
or lost; equally, these references are not secret against anyone who can guess the inputs. (The
plan named a "subject-key secret, not rotatable without a full rekey"; the code has none.)

### Credentials and passwords

- **LMS web-service token** (`assess_ws_tokens`): create the new token on the LMS, replace the
  site's entry in the file, recreate the worker (`compose up -d --force-recreate
  vektra-assess-worker`: the bind mount may still show the old file), run the setup check
  (`token_works` must be `OK`), then delete the old token on the LMS. See the
  [service account](assess-moodle-service-account.md#token-creation-and-rotation).
- **SMTP account** (`assess_smtp`): replace the file, recreate the worker, then
  `POST /api/v1/assess/ops/smtp-test` and read its result.
- **Role passwords** (`assess_db_api_password`, `assess_db_worker_password`): replace the file,
  `compose run --rm vektra-assess-db-init`, then recreate the service that holds the password
  (`compose up -d --force-recreate <service>`).

### Cadence: rotation, retirement and backup retention

Crypto-shredding (the retention purge and the erasure) removes a session's wrapped DEK from the
live database, not from a database backup taken before the purge. A backup plus the KEK that was
active when it was taken can therefore still open a purged session, until either the backup
expires or that KEK is destroyed (ARCH-079 as amended by plan 12). The rules that follow from
it (plan 13 design note; they are operational policy, not enforced by code):

- Set `VEKTRA_ASSESS_DB_BACKUP_RETENTION_DAYS` to the real retention of your database backups.
  The worker only warns at startup when it is unset; nothing else reads it.
- Rotate `assess_kek` and `assess_transcript_kek` at least once per retention interval (the
  smallest `retention_days` of your sites' privacy settings).
- A retired kid stays in the offline key backup (never in a live keyring) until the newest
  database backup taken while any row was under it has expired, that is
  `VEKTRA_ASSESS_DB_BACKUP_RETENTION_DAYS` days after the re-wrap that retired it finished. Then
  destroy every copy of it and record the date.
- What this does and does not buy: a purged session stays recoverable from a backup for as long
  as that backup is kept, whatever the rotation; destroying a retired kid before its backups
  expire would make the whole of those backups unreadable, not only the purged rows. The cadence
  bounds how many retired keys exist and gives each one a date after which it must be gone. The
  restore drill below must use a backup that is still within its retention.

## Shredding

`shred_session` and `shred_transcript` null the wrapped DEK first, then delete the ciphertext rows
and return per-table counts. They refuse a session that is not CLOSED. Verify a purge by counting
rows, not by trusting a status.
