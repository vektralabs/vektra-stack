# Lesson: integration gap tracking in assembly plans

**Date**: 2026-03-10
**Source**: Phase 2 Wave 5 PR #32 review — 5 gaps found post-implementation
**Severity**: process gap — features deferred to assembly plan but never tasked

---

## Problem

In a multi-wave development process, component plans often defer integration
work to a later assembly plan. The component plan documents the deferral
("wired in infra-phase2") but the assembly plan is generated independently
and does not scan component plans for deferred items.

Result: features are explicitly deferred with a clear target plan, but the
target plan never picks them up. The gap is invisible because:

1. Each plan passes its own validation (provides/requires, topology, tests)
2. The wave boundary checklist validates structural properties, not feature completeness
3. Deferred items are scattered across docstrings and comments, not tracked centrally
4. The assembly plan author (human or LLM) writes tasks based on architecture docs, not by grep-ing "infra-phase2" across the codebase

## Evidence from Phase 2

### How deferrals were created

During Waves 1-4, five component plans deferred integration work to
"infra-phase2" (Wave 5):

| Wave | Plan | Deferred item | Location of deferral |
|------|------|---------------|----------------------|
| 1 | index-hybrid | Reindex job execution (extract/chunk/embed/store) | reindex.py docstring + design note |
| 0 | shared-protocols-phase2 | WebhookEventEmitter registration | events.py module docstring |
| 3 | component-analytics | Analytics retention cleanup job | service.py comment + config.py |
| 0 | shared-protocols-phase2 | Soft-delete retention cleanup job | config.py field description |
| 4 | component-learn | Learn ingestion wiring via ProviderRegistry | service.py docstring + api.py comment |

### How the assembly plan missed them

The infra-phase2 plan was generated from:
- architecture.md (high-level component wiring description)
- Phase 2 scoping plan (wave structure and dependencies)
- provides/requires graph (inter-plan dependencies)

It was NOT generated by scanning the actual source code or the docstrings
of completed component plans. The provides/requires system tracks module-level
dependencies ("plan X provides `analytics-service`, plan Y requires it") but
not intra-module deferred work items ("this function is a skeleton, to be
completed by plan Y").

### Why existing checks didn't catch this

| Check | Why it missed the gaps |
|-------|----------------------|
| provides/requires validation | Tracks module/artifact availability, not implementation completeness |
| Wave boundary checklist | Validates structural properties (ownership, imports, protocols), not "does every deferred TODO have a matching task" |
| Automated CHK-* checks | Verify plan internal consistency, not cross-plan TODO resolution |
| PR bot review | CodeRabbit identified the reindex skeleton (GAP-1) but not the other 4 gaps |
| Manual review | Reviewer focused on code correctness, not on grep-ing for "infra-phase2" in docstrings |

## Root cause analysis

The process has a tracking gap for **intra-code deferrals**. There are three
types of deferred work in the system:

| Type | Example | Tracked by | Status |
|------|---------|-----------|--------|
| **Plan-level** | "Plan X provides token Y, plan Z requires it" | provides/requires YAML | Works well |
| **Architecture-level** | "Phase 2: WebhookEventEmitter" | architecture.md sections | Partially tracked |
| **Code-level** | "wired in infra-phase2" in a docstring | Nothing | **Gap** |

Code-level deferrals are the most dangerous because they are:
- Written informally (comments, docstrings, not structured data)
- Scattered across many files
- Created by the implementing agent during task execution, not during planning
- Invisible to plan validation which reads plan files, not source code

## Proposed process improvement

### Option A: assembly plan codebase scan (recommended)

Before finalizing an assembly plan, scan the codebase for references to the
plan name:

```bash
# Find all code-level deferrals targeting this plan
grep -r "infra-phase2\|Wave 5\|assembly plan" \
  --include="*.py" \
  --exclude-dir=tests \
  --exclude-dir=.s2s \
  src/ vektra-*/src/
```

Each hit must map to a task in the assembly plan. If it doesn't, add the task.

### Option B: structured deferral registry

Add a `DEFERRED.yaml` file to `.s2s/` that component plans update when they
defer work:

```yaml
deferrals:
  - id: DEF-001
    source_plan: index-hybrid
    target_plan: infra-phase2
    description: "Complete reindex job execution (extract/chunk/embed/store)"
    location: vektra-index/src/vektra_index/reindex.py:77
    status: open
```

The assembly plan generator reads this file and creates tasks for each open
deferral. Wave boundary checklist item: "Are all DEF-* entries targeting
this wave resolved?"

### Option C: wave boundary checklist addition

Add a new section to the wave boundary checklist:

```
## M — Deferred work resolution

| # | Question | Answer | Note |
|---|----------|--------|------|
| M1 | Has the codebase been scanned for references to this wave/plan name? | YES/NO | |
| M2 | Does every code-level deferral have a matching task in the plan? | YES/NO | |
| M3 | Are there zero "skeleton", "placeholder", or "not implemented" markers in code produced by prior waves that reference this wave? | YES/NO | |
```

**Recommendation**: implement Option A immediately (zero tooling cost) and
Option C for future waves. Option B is valuable for larger teams but
over-engineering for the current project size.

## Broader lesson

The s2s plan validation pipeline catches **structural** issues (missing
dependencies, import violations, ownership conflicts) very well. It does NOT
catch **completeness** issues (deferred work that was promised but never
tasked). This is the same gap identified in `s2s-plan-codebase-validation.md`
but at a different level: that lesson covers "plan vs codebase inconsistency
at generation time"; this lesson covers "deferred work tracking across waves."

Both share the same root cause: **LLM agents read architecture docs for
planning but don't read source code for verification**. The fix is the same:
add a codebase reading step, but at different points in the process:
- Generation time: read code to avoid proposing changes that conflict with existing code
- Assembly time: read code to find deferred work that needs to be picked up
