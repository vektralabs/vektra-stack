## Overview

B.1 lists this as plan-phase priority #1. Every START gate input (BR-006 b/c/d/e/f), the attempt selection (BR-012), "fully graded" (BR-014), the disclosure boundary (BR-011) and the grader list (REQ-082) come from Moodle web services read with a dedicated service account. OQ-025 and OQ-031 ask whether those reads are possible at all on 4.3 and 5.2. ARCH-070 turns the answer into data: typed readers return `Readable(value) | Unreadable(reason)`, a setup check probes each reader against seeded fixtures and persists a per-site, per-release capability matrix, and every unknown defaults to UNREADABLE, which fails closed.

This plan delivers:
(a) reproducible Moodle 4.3 and 5.2 Docker dev environments in the vektra-moodle repo, with scripted service-account provisioning and fixture seeding through Moodle's own `testing_data_generator`;
(b) the spike run as code: the hardened httpx WS client and typed readers in `vektra_assess.moodle`;
(c) the `assess_site_capabilities` matrix with release-change invalidation and a daily re-probe;
(d) the REQ-079 setup check, as a worker job triggered through the API;
(e) a spike findings document.

## Design Notes

- **Package split (keeps contract (c) honest).** `vektra_assess.moodle` (WS client, readers, probes, setup-check items) is importable ONLY by `vektra_assess.worker.*`. The API side never needs it. Matrix *reads* (`site_readiness`, `capability(site, flag)`) live in `vektra_assess.capabilities`, a DB-only module with no httpx import that both the API and the worker can import. The setup-check endpoint in `vektra_assess.api` only inserts a job row and reads the content-free report.
- **Result type.** `Readable[T](value: T, evidence: ShapeEvidence)` / `Unreadable(reason: UnreadableReason, detail_code: str)`, with `UnreadableReason` = function_not_in_service | access_exception | unknown_shape | partial | breaker_open | timeout | size_cap | tls | redirect | version_unsupported | not_probed | release_changed. No `None`, no exception escapes a reader. Consumers must pattern-match; mypy `assert_never` enforces exhaustiveness.
- **Strict per-version models.** `vektra_assess/moodle/models/v4_3/` and `.../v5_2/` hold Pydantic models with `ConfigDict(extra="forbid", strict=True, frozen=True)`. The version is chosen from `core_webservice_get_site_info.release` (major branch). An unknown branch makes every reader Unreadable(version_unsupported). An extra or missing field makes the reader Unreadable(unknown_shape). A Moodle error envelope delivered as HTTP 200 (`{"exception","errorcode","message"}`) is detected before model parsing and never parsed as data. Only `errorcode` is kept, because `message` can echo data. Point releases that add fields therefore fail closed on purpose; the release-change invalidation forces a re-probe anyway.
- **Anti-corruption.** Readers return domain values (`QuizCloseInputs`, `AttemptSummary`, `ReviewVisibility`, `RubricDefinitionView`, `GraderList`, ...) in `vektra_assess/moodle/domain.py`, never raw Moodle shapes. Moodle ids appear only inside these values, never in anything a client sends (REQ-095, NFR-014).
- **WS client (`MoodleWsClient`).**
  - httpx.AsyncClient with `follow_redirects=False` asserted in a unit test; any 3xx becomes Unreadable(redirect) and the Location header is never followed.
  - TLS verified against `VEKTRA_ASSESS_MOODLE_CA_FILE`, else the system store.
  - Plain http only when `VEKTRA_ENV=development` AND `VEKTRA_ASSESS_MOODLE_ALLOW_HTTP=true`. A startup step refuses it otherwise, so this dev convenience can never be live in production.
  - Per-call timeouts (connect 3 s, read 10 s, configurable).
  - The response is streamed with a byte cap (default 8 MiB JSON, 10 MiB per file, matching the REQ-101 limits) and aborted on overflow.
  - The token travels in the POST body (`wstoken`), never in a URL that could be logged.
  - The token is read from `/run/secrets/assess_ws_token_<site_id>` at call time, never from env or DB.
  - **Logging**: wsfunction, site_id, http status, duration_ms, bytes, errorcode. Never bodies, params or token. A test captures all structlog output at DEBUG and greps it.
- **Breaker and rate cap.** The per-site circuit breaker is closed → open after N consecutive transport/5xx failures (default 5), cools down (30 s), then half-open allows one probe. Open means Unreadable(breaker_open), never an error page. A global async token bucket (`VEKTRA_ASSESS_WS_RPS`, default 10) is shared by every caller in the worker, including render checks, gate refresh and bursts of Starts. Both are in-memory in the single worker process (single replica, COMP-003).
- **Egress / SSRF guard: decision = COPY into vektra_shared, do not move.**
  - `vektra_learn.api._resolve_and_validate_url` denies every private address. On-prem Moodle hosts are usually private, so that policy is wrong for assess, and changing learn's behaviour is out of scope.
  - The new `vektra_shared/netguard.py` provides `resolve_pinned(url, *, allowed_hosts, allowed_cidrs, deny_private)`. It resolves once, validates ALL addresses, and returns the pinned IP plus the original hostname.
  - The assess client connects to the pinned IP and passes `extensions={"sni_hostname": host}` with a Host header, so TLS still verifies against the hostname. A test against a self-signed CA proves both rebinding protection and certificate verification.
  - The allowlist is the registered site's `base_url` host only (assess_sites, plan 1).
  - Learn keeps its function. Unifying the two is recorded as a follow-up DEBT item in Notes and is not done here.
- **Capability flags (ARCH-070) plus the additions this plan needs.** quiz_overrides, assign_extensions, assign_cutoff, quiz_grace, attempt_state, per_student_timelimit, review_html_filterable, rubric_display_settings, module_visibility_per_student (OQ-031(1)), loginas_crosscheck (OQ-031(2), COMP-004), graders_resolvable (REQ-082), enrolment_readable (re-check), release_state (BR-010), grading_state (BR-014). Each row is readable | partial | unreadable. PARTIAL counts as unreadable for every gate (REQ-091). Never-probed means unreadable.
- **Probes are fixture-backed.** A probe passes only if the reader returns exactly the expected value recorded in the site's probe manifest. For example, the seeded user override with timeclose T must come back as T for that user. "The call returned 200" is not evidence (project rule: verify empirically). `evidence_hash` = sha256 over the canonical *shape signature* (function, keys, types, counts) plus the release. It is content-free.
- **Service-account checks that WS cannot see.**
  - Interactive login disabled: READABLE via `core_user_get_users_by_field(id, self)` → `auth == 'webservice'` (spike-verified on both). `nologin` cannot pass, because WS refuses it. Items that cannot be verified report `UNVERIFIABLE`, which counts as not OK.
  - The plugin plan (P1) may add a Moodle-side attestation for them, recorded as a plugin statement, not a verification.
  - "Not a site admin" uses `site_info.userissiteadmin`.
  - "Not the ingestion account" compares site_info username/userid against `VEKTRA_ASSESS_INGEST_ACCOUNT_USERNAME`; if that setting is unset, the item is UNVERIFIABLE.
  - "Denied function fails" calls a harmless read-only function deliberately left out of the service (`core_course_get_categories`). The probe never calls a write function, so it cannot do damage if it unexpectedly succeeds.
  - "No grade-write function" (REQ-079 as amended 2026-11-01: the control is the function list, not the capability set; reading rubrics needs managegradingforms) is checked from site_info `functions[]`: no grade-write wsfunction may be in the service, using a hard-coded denylist (mod_assign_save_grade(s), mod_assign_submit_grading_form, core_grades_update_grades, mod_quiz_* override/regrade writers, core_grading_* save). The capability-level side is checked on the probe course with `core_enrol_get_enrolled_users_with_capability(moodle/grade:edit, mod/assign:grade?)`. See the Notes risk.
- **Report shape.** `assess_setup_check_reports.items` is a list of {name, result OK|MISSING|UNVERIFIABLE, reason_code}, plus the capability rows. It is content-free: no Moodle text, no emails, no ids beyond site_id. The feature is available for a site only if the latest finished report for the CURRENT release has every item OK and every close-time flag row is fresh (`checked_at` within 26 h).

## State & Data Lifecycle

| State element | Created by | Updated by | Invalidated/Deleted by |
|---------------|-----------|------------|------------------------|
| assess_site_capabilities rows | probes.py during a setup-check run (E/F) | every setup-check run (daily tick, manual trigger, release change) | release change → all rows unreadable/release_changed (D); staleness > 26 h read as unreadable; rows deleted on site deregistration (FK ON DELETE CASCADE) |
| assess_setup_check_reports rows | POST setup-check (F) | worker handler (running → done/failed) | retention tick keeps last 30 per site (handler deletes older in the same run); cascade on site deletion |
| assess_sites.last_seen_release | first setup check | observe_release on change | site deletion |
| assess_sites.probe_manifest | operator registration / seeder output upload | re-seed | site deletion |
| Per-site circuit breaker (memory) | first call to a site | each call outcome | process restart; cooldown → half-open |
| Global WS token bucket (memory) | worker start | each call | process restart |

## Testing Approach

The core suite is hermetic. Readers run against an httpx `MockTransport` that replays recorded responses from the real 4.3 and 5.2 envs, plus mutated variants that each hit exactly one Unreadable reason. A response that cannot be classified fails the test, never passes it.

The live contract suite (`-m moodle`) runs against the Docker envs. It is the only evidence for OQ-025/OQ-031: the flag table in the findings doc is generated from its output artifact, not hand-written.

DB behaviour (release invalidation, staleness, readiness) runs against testcontainers Postgres and asserts row counts.

### Test Infrastructure

- **Required**:
  - Moodle 4.3 and 5.2 Docker envs with the provisioned service account, negative accounts and seeded fixtures (live suite);
  - recorded WS responses (hermetic suite);
  - testcontainers `pgvector/pgvector:pg16` (matrix/migration tests);
  - a self-signed CA + local TLS server (netguard/TLS tests).
- **Provided by**:
  - task group A (envs, provisioning, seeding);
  - task group C (recorder + recordings);
  - plan 1 (assess package test scaffold, `test-assess` CI job);
  - this plan's G tasks (contract workflow).
- **False-pass guard**:
  - `-m moodle` tests `pytest.skip` with reason `BLOCKED: VEKTRA_ASSESS_MOODLE43_URL unset`, never pass silently.
  - The contract workflow fails if the collected `moodle` test count is 0 or if any flag is `not_probed`.
  - The seeder self-check fails the env bring-up if a fixture is missing.
  - The hermetic suite asserts that every reader has at least one recording per version; a missing recording fails, it does not skip.
