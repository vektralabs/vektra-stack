## Overview

Sets up GitHub Actions CI with three workflows: linting/type-checking with boundary enforcement, integration tests using the Docker Compose stack, and shell script validation. Hard NFR gates (search <500ms, startup <60s, 100% audit log completeness, 100% error actionability) run in the integration workflow and block merges. Performance targets (query latency) are measured and logged but do not block merges in Phase 1 per EX-004.

## Design Notes

- Three workflows: `lint.yml` (on every push/PR), `integration.yml` (on PR and main branch), `shell-scripts.yml` (on PR).
- Integration workflow uses Docker Compose to spin up the full stack, runs all integration tests including REQ-032 flow, validates hard NFR gates, tears down after.
- import-linter runs in `lint.yml` as a separate step (not pytest). Boundary violations fail the PR.
- Performance measurements use pytest-benchmark; results logged to job summary but only NFR-002 (search) is a hard gate.
- CI uses GitHub Actions service containers for PostgreSQL is an alternative but Docker Compose is preferred for parity with production deployment.

## Acceptance Criteria

- [ ] `lint.yml` catches import boundary violations and fails the PR
- [ ] `integration.yml` runs REQ-032 full flow and passes on a clean run
- [ ] NFR-002 (search <500ms p95) blocks merge if exceeded
- [ ] NFR-004 (startup <60s) blocks merge if exceeded
- [ ] NFR-007 (100% audit log) blocks merge if any authenticated request missing from audit_log
- [ ] NFR-009 (100% error actionability) blocks merge if any normative error code has empty remediation
- [ ] Performance target violations (NFR-001 query latency >20% above target) appear as job summary warnings, not failures

## Testing Approach

The CI workflows are themselves the testing infrastructure. Validate locally by running `act` (nektos/act) to simulate GitHub Actions, or by manual trigger on a feature branch. The integration test suite is independently runnable with `pytest tests/integration/` against a local Docker Compose stack.

## Integration Notes

All integration tests depend on the Docker Compose stack from infra-docker. The sample PDF committed to `tests/fixtures/` is also used by the `make demo` target (infra-makefile plan). Test teardown must clean up all database state between test runs (use pytest fixtures with transaction rollback or database truncation).
